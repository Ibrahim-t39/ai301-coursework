# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| repo-in-use | Repo facts: "last push to any branch" date and "latest release" date, compared to today (live mode) or the bundle's capture date (eval mode) | Pass if the last push to any branch is within 90 days of the reference date. A repo with no releases at all can still pass on push activity alone; releases are not required. | required |
| maintainer-alive | Repo facts: the "archived:" flag, the dates and authors of the last 5 default-branch commits, and the maintainer first-response sample | Fail immediately if archived is "yes". Otherwise pass if EITHER at least one of the last 5 default-branch commits was authored by a human (not a `[bot]` account merging dependency-bump automation) within 90 days of the reference date, OR the maintainer first-response sample contains at least one entry with a stated numeric response time (not "no maintainer comment in thread"). | required |
| unclaimed | The issue's own "assignees" and "linked PRs" facts, plus claim comments in the thread | Pass if assignees is "none" AND no linked PR is in the "open" state (a closed or merged linked PR is a past, not active, claim) AND the thread has no *recent, live* "I'm working on this" / "I'll take this" claim from a human. A claim is lapsed, not active, when it is followed by a long silence with no further activity from that claimant through the reference date — e.g. a stale-bot notice, a maintainer "bump" with no reply, or simply months with no update — and does not fail this check on its own. Fail only when a claim looks current: recent (roughly within the last 90 days of the reference date) with no sign of abandonment. | required |
| scope-bounded | The issue body and its comment thread | Pass if the issue describes one bounded deliverable with a clear expected outcome, completable in one PR by one contributor. Touching several files in service of that single described outcome (e.g. a docs task that adds one new page and updates a few pages that pointed to the old guidance) still passes — judge by whether there is one cohesive objective, not by file count. Fail if any of: (a) the issue explicitly says it's a tracking/umbrella/megaissue listing sub-items meant to be split across multiple contributors/PRs; (b) the thread shows the core approach or design is still being debated with no maintainer decision recorded; (c) the issue is an open-ended, codebase-wide initiative inviting many parallel PRs rather than naming one fix (look for phrasing like "PRs welcome, big or small" plus many linked PRs already chipping at it); (d) the issue is a bare feature request with no maintainer/collaborator endorsement (no maintainer comment in the thread, no newcomer-facing label) and a product decision about whether/what to build is still open; (e) it's a pure usage/support question with no change being requested; or (f) the thread shows a history of repeated abandoned attempts — multiple closed/unmerged linked PRs, or a recurring pattern of contributors claiming the issue and later being unassigned for inactivity — which means the friendly label is hiding real difficulty regardless of how settled the approach now looks. A short body, a missing repro, an old open date, or a plan that touches several related files does not by itself fail this check. | required |
| policy-allows-ai | The "contribution policy" line under Repo facts (or CONTRIBUTING.md / dedicated AI-policy files / PR templates in live mode) | Pass unless the policy states an outright ban on AI-generated or AI-assisted contributions ("we do not accept AI-generated code"). Conditions — disclosure, personal understanding, testing, human review before submitting — are terms to follow, not bans, and pass. No stated policy passes. | required |
| newcomer-signal | Issue labels (e.g. "good first issue", "help wanted", "easy") and the opener's author_association | Pass if the issue carries a newcomer-facing label OR was filed by someone with OWNER/MEMBER/COLLABORATOR association. | preferred |
| fast-response | The maintainer first-response sample | Pass if at least one sampled response was under 14 days. | preferred |

## Verdict rule

Accept only if every required check (repo-in-use, maintainer-alive, unclaimed, scope-bounded, policy-allows-ai) grades pass. A fail on any required check rejects the issue. `unclear` on a required check counts as fail: a first issue whose liveness, claim status, scope, or policy I cannot verify from the evidence is not one to take.

Preferred checks (newcomer-signal, fast-response) never change the verdict. Among accepted issues, rank higher the ones passing more preferred checks and fitting the profile in `scope.md` better; say in the summary what made the top-ranked one fit.
